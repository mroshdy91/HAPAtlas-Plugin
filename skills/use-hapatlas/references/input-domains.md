# Engineering input domains

HAPAtlas automates HAP input entry; it does not choose engineering values. Preserve explicit units, references, and provenance.

## Project and weather

Start with `project-baseline` and keep four scopes separate: HAP 5.1 Project > Properties when applicable, View > Preferences > Project, General/program preferences, and Phase 1 Weather. HAP 6.x removed the legacy Project Properties dialog and exposes only `.HAP` file identity. Use `hapatlas_project_properties_manage` only in HAP 5.1 for name/number/date/contact/manager/notes; a saved-name change requires engineer-controlled Save As. Use `hapatlas_project_preferences_manage` only for LEED, project 62.1, project 90.1, and currency. Matching values are no-ops. A supported ASHRAE edition change requires dry-run impact review and explicit engineer confirmation. On HAP 6.3, HAPAtlas follows Carrier's traced dependency order: preferences, Space Type resets, Space Model resets, then each Air System using an edition-specific ASHRAE 62.1 sizing method. HAP 5.1 mutation is limited to a project without Spaces, Systems, Plants, or Buildings; populated migration and differing LEED/currency remain guarded. Keep each system's `ventilation_sizing_method` separate. Jurisdiction, code notes, building use, and calendar intent are plan provenance. Resolve weather only in Phase 1 by exact installed identity; never substitute a nearby city without user approval.

## Schedules and usages

Model named profiles and explicit month/day assignments. Do not infer a United States weekend. Map Monday through Sunday, holidays, and design days explicitly. Keep people, lighting, equipment, fan, and thermostat schedules semantically distinct. Exact library `inspect` returns fraction values as `0.0-1.0` and thermostat occupied states without exposing HAP sentinels. HAP 5.1 thermostat hours may omit temperatures because setpoints belong to the referencing system zones; combine both inspections rather than inventing them. Supply profile temperatures when the selected HAP 6.3 native path requires them.

Do not force HAP 6.x object names onto HAP 5.1. HAP 6.x has a reusable Project Library `space-type`. HAP 5.1 instead exposes an ASHRAE ventilation `space-usage` selector inside each Space, or `User-Defined` OA inputs. Complete archive/template Space evidence is separately named `source-space`. Search/inspect is available; HAP 5.1 usage mutation remains in the later Space workflow and must not be simulated with a source-Space clone.

Represent people by exactly one basis: direct count, people per area, or area per person. When the native source exposes activity sensible/latent heat, fixture type, ballast multiplier, or separate people/lighting/equipment radiant fractions, carry those exact fields instead of assuming a generic activity or fixture. The radiant-fraction fields are native HAP 5.1 controls; HAP 6.3 must report a representation boundary because its engineer-visible Space Type model does not expose them. Use either one shared infiltration basis or independent cooling and heating bases; never average or copy one season into the other without an engineering instruction.

Attach each schedule only to the load that actually uses it. A native zero equipment load with no equipment schedule is valid and must not be replaced by a fabricated schedule merely to satisfy object shape.

## Envelope

Floor and ceiling ownership also differs by adapter. HAP 6.x has reusable Floor and conditional Ceiling assemblies that are later assigned to engineer-authored geometry. HAP 5.1 owns one conditional Floor directly on each Space and represents a ceiling load as one of up to two Space Partitions with `type=ceiling`. A floor above conditioned space needs no heat-transfer data; a ceiling partition is needed only when an adjacent unconditioned/partially conditioned/different-temperature region exists. Never report these concepts as absent merely because HAP 5.1 has no matching Project Library node.

Prefer installed libraries. Search and inspect the exact category before its dedicated manager: `wall`, `roof`, `window`, `door`, or exterior `shade`. Preserve ordered layers, film resistances, adapter-specific opening-performance meaning, and complete Shade geometry. When explicit fields override a native template, report the derived difference and `LIBRARY_OVERRIDE`. Reject malformed inputs, not merely unusual values. Simple Window actions, Detailed Window create/edit, Door definition create/edit/import, and exterior Shade definition create/edit/import are Available; Detailed Window import remains Candidate. Floor, Ceiling, placement, and assignment remain guarded; lower-level research evidence is not a public fallback.

For a custom HAP 5.1 exterior above-grade Wall, provide at most eight ordered material layers between explicit inside/outside films and provide `expected_u_value` when matching a benchmark. HAPAtlas uses Carrier's fixed native layer sequence, derives U, and stops preflight on a tolerance mismatch; never remove that check merely to make an apply pass. HAP 5.1 inside-surface, interior, and below-grade Wall paths are not promoted.

For a custom Roof on either adapter, public layers are exterior-to-interior and use direct visible thickness, density, specific heat, and thermal resistance; conductivity is not a direct Roof-form input. HAP 5.1 reverses that public order into its fixed native inside-to-outside slots and allows at most eight layers. HAP 5.1 exposes outside surface color/absorptivity only; HAP 6.3 also exposes inside long-wave surface properties. `expected_u_value` remains an assertion. Individual material-library references are guarded on HAP 5.1, while exact complete-Roof import is Available through the dedicated action. Roof area, slope, exposure, geometry, skylights, and assignment never belong to `hapatlas_roofs_manage`.

For a Simple Window, use only the fields visible in the selected adapter. HAP 6.3 requires U-value, SHGC, and visible transmittance and rejects reusable-definition width/height. HAP 5.1 requires U-value, native overall Shade Coefficient, and nominal width/height and rejects SHGC/VT. These are not silently converted cross-version.

For a Detailed Window, select the exact method-specific action and preserve pane order from outermost to innermost. Custom create and exact-ID edit are Available; complete-library import remains Candidate. HAP 5.1 requires exact inspected `window-frame`, conditional `window-gap`, `window-internal-shade`, and one-to-three `window-glazing` items. HAP 6.3 uses exact frame/gap/internal-shade choices but takes visible pane name, thickness, conductivity, Low-E, transmissivity, and reflectivity directly; absorptivity is derived and there is no glazing-item library. Carrier derives native performance. `expected_performance` is only a rollback-triggering assertion and is never written. HAP 6.3 direct panes are `CUSTOM_INPUT` under `prefer_library` and rejected under `library_only`.

Window placement/quantity/host assignment, assigned edit, implicit method conversion, Skylights, and exterior Shades do not belong to these promoted Window actions.

For one reusable Door definition, use only `hapatlas_doors_manage` after exact `category: door` inspection. HAP 5.1 has no Door Type selector: use positive `gross_area` and `opaque_u_value`; `glass_area` is absolute area from zero through gross area, and positive glass area also requires `glass_u_value`, native `glass_shade_coefficient`, and `glass_shaded_all_day`. With zero glass area, omit all glass inputs even if inspection exposes Carrier values under read-only `inactive_glass_defaults`. HAP 6.3 instead requires `door_type`: `opaque` uses opaque U only; `glass` uses glass U/SHGC/VT; `opaque_with_lites` uses both U-values, glass SHGC/VT, and `glass_fraction_percent` strictly between 0 and 100. Never treat that percentage as a 0.0–1.0 fraction, convert HAP 5.1 Shade Coefficient to SHGC, or add reusable dimensions to HAP 6.3. All three unassigned Door definition actions are Available and require complete fresh readback.

ProjectSpec preserves both `opening_types[].shgc` and `opening_types[].shade_coefficient` because the visible Simple and derived Detailed forms do not expose the same basis. Use SHGC only for HAP 6.3 assertions/ratings and native Shade Coefficient only for HAP 5.1. HAPAtlas does not apply an assumed `0.87` conversion. Cross-version comparison reports the representation difference. Standalone exterior-Shade definition geometry has a separate Available manager; its placement and assignment remain guarded.

## Geometry and openings

Use stable external keys and stable edge references. Validate polygons, shared boundaries, overlaps, opening bounds, opening collisions, levels, elevations, and heights before mutation. Do not approximate curves, holes, slopes, or ambiguous edge placement when the adapter does not advertise them.

The polygon area and any supplied native legacy floor area must agree within the documented rounding tolerance. Same-level spaces may share boundaries but may not overlap. Correct the geometry itself; never compensate by changing floor area, density, or load inputs.

HAP 5.1 stores envelope surfaces directly on each Space. Use `ProjectSpec.spaces[].legacy_surfaces` only with the HAP 5.1 adapter. The wall and roof arrays replace the fixed native slot sets and accept named 16-point orientations (`north`, `north_northeast`, through `north_northwest`); a zero-slope roof may use `horizontal`. Supply direct gross areas and exact construction keys. The optional floor merges a typed native floor. Candidate wall inputs accept up to two typed windows and one typed Door reference plus quantity. That consumer action may reference an exact accepted Door definition, but it cannot create/edit the definition or add a second Door type to the same wall. Never pass raw numeric exposure codes. The accepted no-opening benchmark has native input-report proof after user Save/reopen; opening placement/assignment cases remain Candidate until their separate live gate passes. HAP 6.3 must derive surfaces from its building/space-model geometry and rejects this field.

For the same-build public-workflow oracle, a registered immutable project/archive is read-only evidence: inspect the exact source Space, schedules, usage, surfaces, openings, and dependencies, then recreate them inline through the public domain tools. Do not attach a complete source Space or System `library_ref`, create an external whole-model file, or use native object cloning in that acceptance run. Native Space/System cloning remains a separate import transport for an explicit user reuse request; it proves neither typed input coverage nor same-result recreation reliability. HAPAtlas must fail if exact source detail or a named dependency cannot be inspected and rebound.

## Spaces and loads

Keep density bases explicit and mutually exclusive. Convert people, lighting, equipment, outdoor air, and infiltration deterministically per actual space. Preserve separate schedule references. The `input-audit` inspection reports actual native per-space totals, semantic people and infiltration bases, and missing schedule bindings; verify these totals against a native input report before calculation.

For the first HAP 5.1 direct Space slice, use `hapatlas_spaces_manage` only when its exact action appears in the installed acceptance inventory. Submit one inline `space` with `external_key`, `name`, positive `floor_area`, positive `average_ceiling_height`, optional positive `building_weight`, explicit IP/SI units, and engineering provenance. IP means ft², ft, and lb/ft²; SI means m², m, and kg/m². `general.create` omits `hap_id`; `general.edit-existing` requires the exact current native `hap_id`. Do not construct a Building, Space Model, rectangle, polygon, Level, usage/load, Schedule, or surface merely to satisfy input shape. Scout `spaces` must prove native identity/dimensions and unchanged non-General data before calculation or user Save. HAP 6.3 direct Space mutation is not applicable because its visual geometry is engineer-authored.

Use `direct_exhaust_airflow` only in a later promoted Space/Space-Type load action for kitchen and toilet exhaust (cfm in IP, L/s in SI). Do not misuse infiltration as exhaust or add it to the General action. Carrier HAP incorporates direct exhaust into its native replacement/outdoor-air sizing. A separate dedicated makeup-air unit must be represented by a promoted native system workflow; do not invent an independent makeup-air scalar.

In HAP 6.3, a Space Model keeps native copies of its selected Space Type inputs. Saving one reusable definition and Carrier's separate **Apply to All Space Models** command are not the same professional action. Candidate `hapatlas_space_types_manage` definition create/edit must eventually prove assigned Space rows unchanged; the guarded propagation action requires its own impact plan, confirmation, canonical row readback, and result invalidation. Neither action may be simulated through the retired shared writer.

For inspected HAP 6.3 space types, read `people_input_basis`, `people_input_value`, and `people_input_unit` together. `area_per_person_ft2: 200` means 200 ft2/person (5 people/1,000 ft2), not 200 occupants. Use `people_total` only when the reported basis is `people`. Never reinterpret an unknown native basis.

## Space model and zoning

Synchronize the physical building and load model through the adapter's native path. Ensure every conditioned space has the intended zone and every zone is served by the intended system. Treat unserved or multiply assigned zones as blocking validation failures.

## Air systems

Specify the system type, compatible equipment type, zone references, thermostat schedule, supply conditions, safety factors, fan data, economizer, ventilation behavior, terminal minimums, reheat, and plant source where applicable. Use exact native templates when possible. Capability-check every system/equipment combination.

Native split DX fan coil (`ST_SPLIT_DX_FAN_COIL`) and VRF (`ST_VRF`) both use `ET_FANCOILS` in the supported HAP 5.1 and 6.3 builds. They are Candidate portfolio mappings: use exact native library templates and do not generalize them to another enum, equipment class, or HAP build. HAP 5.1 imported templates have isolated sizing/source-report proof, but the agent must still request live inspection, user Save/reopen, and native report verification before treating that portfolio as accepted.

For system inputs, preserve cooling and heating coil used state, semantic source, bypass, auto-size, reset, sizing factor, separate sensible/latent cooling safety, supply conditions, fan configuration, return plenum, ventilation control/method, preheat, reheat/zone heat source, water delta-T, terminal type, minimum airflow, terminal temperature, and zone air-distribution configuration/basis whenever exact inspection exposes them. Supply `air_distribution` with `air_distribution_effectiveness_basis: ashrae_62_1_table`; do not send a nominal effectiveness because Carrier derives the active cooling/heating value from its table. HAPAtlas maps this to Carrier's separate distribution and specification-basis properties and suppresses the dormant native effectiveness value. User-specified effectiveness is not promoted. A minimum-airflow fraction is decimal `0.0–1.0` on the wire and becomes native percent exactly once. Do not request HAP 5.1 ASHRAE 62.1-2019 sizing; choose an installed legacy method or `sum_space_requirements` on an engineering basis.

When exact native inspection exposes occupied and unoccupied heating/cooling setpoints, send them as explicit system inputs. They override thermostat-profile defaults. Keep ASHRAE 62.1 at the same per-system scope: select the source system's exact `ventilation_sizing_method` or an engineer-approved alternative, never a project-wide inferred edition.

Read fan performance basis and unoccupied operation semantically. HAPAtlas maps HAP 5.1 numeric fan-unit/control enums and HAP 6.3 named enums to the same meanings; do not treat their raw native codes or version-specific labels as engineering differences.

Treat native HAP 5.1 source value `irrelevant` literally. If reheat is active, `irrelevant` is an input mismatch requiring an engineer-selected promoted source; it is not evidence that HAPAtlas failed to inspect the field.

Interpret every native source code in the context of its owning field. In HAP 6.3 the same raw enum number may represent chilled water for central cooling and electric resistance for terminal reheat. Compare water delta-T only when an active source consumes that loop; never use an inactive stored default to manufacture a parity mismatch.

## Plants and equipment

Model equipment before dependent plants, and plants before alternatives/buildings. Preserve chillers, boilers, heat rejection, quantities, sequencing, design temperatures, flow assumptions, system connections, and source references. Do not claim plant sizing until the selected adapter reports it promoted.

Chiller definitions are a separate engineer-visible chapter. Scout `plants`, search then inspect exact `category: chiller`, and use only `hapatlas_chillers_manage` for one cooling-only definition. Air-cooled packaged-scroll create/edit is Available on both adapters. Water-cooled centrifugal create/edit is Available on HAP 5.1 only for the accepted exact one-Chiller/Cooling-Tower/VAV-CHW portfolio and remains Candidate on HAP 6.3; exact import remains Candidate on both. The water-cooled branch conditionally owns ECWT and condenser flow, preserving total/per-capacity/delta-T basis. After mandatory readback, Plant may consume the identity but never rewrite the definition. Stop at incompatible branch fields, heat recovery/free cooling, performance mutation, type conversion, assigned edit, duplicate, or delete.

Heat rejection is also a definition chapter before Plant composition, but its engineer-visible name is version-specific. HAP 5.1 Project Libraries > Cooling Towers uses `hapatlas_cooling_towers_manage`: `cooling_tower` create/exact-ID unassigned edit is Available, while Dry Cooler, Geo/Well/Surface Water, and exact import remain Candidate. HAP 6.3 Project Libraries > Heat Rejection uses Candidate `hapatlas_heat_rejection_manage`. Both model the same three semantic branches, but each exposes different visible fields and has independent acceptance. Submit only the active branch, keep IP/SI and total/per-capacity/delta-T bases explicit, and require exact native readback. Plant composition may later assign only that verified identity; it must never create, edit, import, or convert the definition.

Boiler definitions are a separate shared visible chapter. Scout engineering `plants`, search/inspect exact `category: boiler`, retrieve `boiler-workflow-v1`, and use only `hapatlas_boilers_manage`. One inline Hot Water Boiler may use Available native-default create or exact unassigned edit; import is non-callable. Create/edit is limited to the supported fuel, autosize/fixed Gross Output, design HWST, total/delta-T flow, overall efficiency, accessory kW, and the exact 90-through-0 user-defined PLR rows. Steam, other PLR models, assigned edit, duplicate/delete, multi-Boiler, and SHW remain guarded.

New Plant composition and System connection are temporarily non-callable while HAPAtlas adds exact pre-native portfolio resolution. Do not retrieve or invent `plant-workflow-v1`; use `adapter-capabilities.callable_actions` and stop when `hapatlas_plants_manage` is absent. Existing accepted Plants remain inspectable/calculable/reportable. A HAP 5.1 Schedule of Eqpt. row showing `<none>` remains a blocking broken reference, not a cosmetic label.

## Alternatives and Buildings

HAP 6.3 Alternatives reference space models, systems, plants, utility rates, and calculation status. HAP 5.1 exposes the equivalent top-level design grouping as Buildings. Use external keys so the semantic contract remains stable across adapters.

## Units

Accept IP or SI wire inputs through unit-neutral field names. HAPAtlas normalizes and converts once. Do not change HAP display units unless a separately promoted preference explicitly requests it.
